# Proposal: externally held audit-chain head

Status: design and owner decision, 25 September 2026. No destination, account, subscription or job has been configured. The current global SQLite audit chain verifies retained rows in `rowid` order and returns `(checked, head_hash)`. Deleting its latest rows leaves a shorter chain that still verifies. [Verifier source](https://github.com/zuluteam247/Pinak_Projects/blob/main/Pinak_Services/memory_service/app/core/database.py).

## What an anchor must prove

After each successful local chain verification, record a small canonical statement: service/database identity, schema/chain version, monotonic sequence (not just current row count), latest audit row ID, UTC time, row count and head digest. Sign or timestamp the statement if possible. The external custodian must retain previous statements, not overwrite one "latest" file. A verifier must fetch trusted prior statements, validate their custody/proof, and check that the retained SQLite chain has the anchored row as the same prefix with the same digest. Simply comparing the current head with the last anchor would flag legitimate later appends. If the anchored prefix is missing, changed or shorter, fail the integrity check and alert. A newly initialized empty DB must not silently replace an already anchored identity.

A trusted anchor detects deletion/rewrite of an anchored tail *after* the anchor. It cannot reveal events never recorded, changes between anchors before the next statement, or compromised custody. A timestamp only proves a digest existed before a time; it does not establish that the operator included every event. Monitor missed anchoring jobs separately and test restore-time verification. Never place the only anchor in the same writable DB, host, backup directory or agent-controlled repository.

## Free destination candidates

| Candidate | Custody and cost | What it adds | Main gap |
| --- | --- | --- | --- |
| OpenTimestamps public calendars, with `.ots` receipts and completed proofs retained by a separate custodian | Calendars say they are free, without API key. Publish only the canonical statement digest; retain the input statement and receipt outside the service. Later upgrade/verify the proof. [Official site](https://opentimestamps.org/), [client](https://github.com/opentimestamps/opentimestamps-client) | A completed proof anchors an existence time beyond the service host and GitHub account. Good independent evidence of an earlier head if receipt/statement survives. | Initial receipt is pending, completion can take time, public calendars can be unavailable. A missing receipt cannot be reconstructed merely from the DB; keeping it only on the host defeats the purpose. Strong independent verification may require a Bitcoin node; explorer-based checks add trust. |
| Separate owner-controlled GitHub public repo with append-only dated anchor files, protected main and a distinct custodian identity | GitHub Free supports public repos; branch protection can restrict force pushes/deletion. [Plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans), [branch protection](https://docs.github.com/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/about-protected-branches), [permissions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository) | Easy public review and automation, if the service identity cannot rewrite/delete anchors and a human owns protection settings. | Same GitHub owner/token as the code fork is not independent custody. Repo owner/admin can change controls, history can be rewritten, and public metadata leaks cadence and perhaps service identity. Do not assume a personal-account repo offers true append-only permissions. |
| Separate owner-controlled Google Drive account/folder, one dated file per anchor, optionally email a second custodian | Existing free storage may suffice for tiny records, subject to account quota. ## Recommendation and owner decision

Prefer OpenTimestamps for independent time evidence **plus** a separately controlled place for statements and receipts. Use a separate owner-controlled GitHub repo as a convenient review ledger only if its credential/custodian is truly isolated from the memory host and current fork; otherwise a separate Drive custodian can hold the small files, with weaker deletion resistance. None is configured or selected. Ask the owner: who will hold the anchor records and receipts, whether publicly visible metadata is acceptable, and the maximum undetected window. A proposed pilot is daily anchors plus an anchor before each backup/restore, with a missed-job alert; that cadence is a design suggestion, not an approved schedule. Verify free-tier terms and account permissions again at setup.

Operational test plan: append events, anchor, append more, remove the anchored tail in a disposable DB and require a failure; remove only unanchored later rows and state the expected blind window; corrupt a retained row; withhold an anchor; restore an older snapshot; simulate calendar outage and receipt upgrade. None of these tests or integrations has been implemented yet.
