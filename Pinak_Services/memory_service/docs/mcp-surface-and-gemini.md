# Pinak MCP surface and Gemini app route

Status: sandbox code and protocol tests, 25 September 2026. No configured desktop agent, Mac install, remote endpoint, Gemini app link or production deployment has been observed.

## Boundaries

The MCP server is a local stdio bridge to the authenticated HTTP service. It is not itself an access-control boundary: API JWT claims carry tenant, project, role and scopes. The server rejects a client ID header that does not match the signed token claim. It does **not** support changing the tenant, project or trusted status just by writing a prompt or setting a header. A local CLI can mint a short-lived token when given the signing secret; this shared-secret design is not appropriate to expose as a remote multi-user app. A future remote server needs per-user OAuth, narrow token issuance and a clear operator threat model.

- `memory.read`: `recall`, `search_context`, `search_rag`, `read_memory`, `list_working`, `list_session`, `list_events`, `list_clients`, `client_summary`, `list_agents`, `list_access`, `list_issues`, `list_schemas`. Each operates only in token tenant/project. RAG search is literal keyword matching, not vector search.
- `memory.write`: `propose_memory`, `create_memory`, `add_working`, `add_session`, `add_event`, `register_client` (ordinary status). `remember_episode` calls quarantine proposal, not direct storage. Direct `create_memory` bypasses quarantine for a token granted write scope, so issuance of that scope must be deliberate; default quarantine is not a universal server-side write gate.
- `memory.admin` plus admin role: `edit_memory`, `delete_memory`, `list_quarantine`, `review_quarantine`, `resolve_issue`, `verify_integrity`. Changing client status to trusted/blocked also requires admin. The MCP `register_client` argument supports it but API enforces the role. `verify_integrity` checks the global audit chain and vector-ID consistency, with `condensed: false`; deprecated `reflect_and_condense` explicitly says condensation is unsupported.
- No delete/update for events, sessions, working entries or audit rows through MCP. Direct admin delete of semantic, episodic, procedural and RAG exists only for authorized fixture or approved real-data workflows. This is not permission to erase a user's real memories.

See `tests/e2e/README.md`, recorded 47-call MCP transcript, seven-layer HTTP results and scoped regression tests. Negative results include 403 for agent edit/delete and read-only write, 404 for cross-tenant reads/edits/deletes/review, and 400 for an SQL column-key attempt. The underlying direct API must remain scoped even when a client does not implement these wrappers. Legacy scripts that assert headers override token identities need migration; the old behavior allowed a signed ordinary token to impersonate a trusted client via a header.

## Gemini app, distinct from Gemini CLI and Enterprise

Google's [Gemini Apps help](https://support.google.com/gemini/answer/17209137?co=GENIE.Platform%3DDesktop&hl=en) describes **Gemini Spark** custom apps: on gemini.google.com, Settings & help > Connected Apps > Custom apps for Spark > enter the MCP server URL. It says the user must have Spark access, be 18+ in the US, use a personal Google account with Keep Activity on; currently English and Spark tasks only. Eligibility and account state have **not** been checked for this owner. The UI may offer advanced credentials if the server does not support Dynamic Client Registration. Google cautions that a custom app can receive other connected-app information and currently requires confirmation for write actions. No linking was attempted.

This Pinak bridge currently runs **stdio** against a loopback HTTP service, not an externally reachable HTTPS MCP URL. It has no observed remote transport, OAuth/Dynamic Client Registration, published hostname, account-link audit, or hardened deployment. It cannot be pasted into Gemini Spark's URL field as-is. A remote adapter and authentication design require separate review and deployment authority. [Gemini CLI](https://geminicli.com/docs/tools/mcp-server/) instead supports local MCP configuration, which the sandbox installer can prepare but has not installed on a real client. [Gemini Enterprise](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server) is a separate Cloud data-store connector requiring HTTPS StreamableHTTP and enterprise configuration. Neither is evidence of Gemini app linkage.

## Prompt-injection boundary

Every stored string, including text created by another agent or copied from an external document, is untrusted. `recall` wraps records with an explicit data-boundary warning, IDs, type and source; it does not treat text as instruction or make outbound fetches itself. The raw structured `search_context`, `read_memory` and list tools still return data that an autonomous consumer could obey by mistake. Service-side labeling and JSON escaping are not a proof of model safety. The recorded fixture test writes malicious text through all seven paths, sees it in MCP recall with labels, and shows zero cross-tenant results. It does **not** run a separate autonomous consumer with unrelated synthetic data and a fake sink; therefore refusal of exfiltration and scope escalation remains unverified.

## Open gaps before production

The 1 MiB request cap, tenant-bound quarantine review and signed client-ID check were regression-tested on local fixtures. The legacy `PINAK_ENFORCE_SCOPES=false` bypass is removed: disabling scope enforcement by environment variable is no longer supported. Search results do not give a guarantee that all matching records fit in an agent context. Direct writes bypass the quarantine review; a malicious writer with `memory.write` can still seed instructions or sensitive data. There is no provider-backed external secrets scanner, no configured real desktop client, no real Gemini Spark endpoint, no separate consuming-agent red team, and no production deployment. The global audit chain remains vulnerable to tail deletion until an independent anchor is operational.
