## Enforceable capture contract

1. **Route and binding (CW §2).** `POST /api/v1/memory/capture` uses the existing router, auth and readiness guard. Authenticate and bind `tenant_id`, `agent_id`, `client_id` to the credential; body/header values are hints to compare, never sources of authority or silent overrides. Mismatch: `403 auth_binding_mismatch`; unauthenticated: 401. Every read/write, including session lookup, task association and recall, is tenant-scoped. Body-free error handling and operational logs/proxies/APM must not leak payloads (CW §5.5; amendment §1).

2. **Identities and canonical event (CW §§3-4; amendment §§1-2).** Preserve all 20 distinct fields: `tenant_id`, `agent_id`, `client_id`, `client_version`, `session_id`, `task_id`, `event_id`, `sequence`, `client_ts`, `received_ts`, `actor`, `event_type`, `payload`, `payload_hash`, `boundary_source`, `source`, `provenance`, `privacy_class`, `retention_class`, `envelope_version`. `event_id` and service-minted `session_id` are ULIDs; `received_ts` is service-assigned and authoritative, while client time is forensic and skew is recorded. A task may span sessions, agents and clients; a session is one logical interaction, never the task itself. `task_id` may be null only in the recorded pre-binding window. Hidden reasoning is forbidden in every payload, including `decision`.

   At session open, optional `client_session_ref` is a stability claim, not authority: when present the service mints once and stores an alias unique per tenant+client; resume finds it, never re-mints. When absent, the service marks `session_identity_source=inferred` and never auto-joins inferred sessions. Sessions never merge; later discovery uses a `continues` relation. Collaborators on a task do not share a service session ID. Session open returns a service-minted ULID, which the client echoes on subsequent events; an optional client_session_ref is an alias, with no nonce or bootstrap token. A task attachment is an explicit, audited, reversible, many-to-many assertion, never inferred by time, directory or proximity. Authority is the owner or an agent acting under a documented task instruction; record who, when and why. There is no bind-once rule. Cross-agent recall is task-scoped within a tenant; session recall is one run; no cross-tenant path (amendment §2 and Task attachment authority; CW §3).

3. **Provenance and policy (CW §§4,4.3-4.6; amendment §1 and Answers to Fo).** The service assigns/verifies authoritative provenance, tenant, privacy and retention; client evidence may be carried or treated as a lower-trust hint but never self-certifies provenance or raises trust. Client-supplied canonical privacy/retention values are rejected, not silently accepted (CW §4.3). Allowed values: `actor` = `user | agent | tool | system | policy`; `event_type` = `message | tool_call | tool_result | response | decision | boundary`; `boundary_source` = `session_start | session_end | task_switch | client_hook | service_timeout | explicit_marker`; `source` = `hook | cli | api | import | system`. Unknown closed member: 422.

   Service classes: privacy = `public | internal | confidential | restricted`; retention = `ephemeral | session | task | durable | legal_hold`. Ordinary work defaults internal; unrelated personal data is confidential and redacted; secret/credential matches are restricted, redacted before persistence and never promotable; already-public content is public. A lower-trust adapter hint can lower, never raise, protection. Raw staging defaults task/30-day TTL unless promoted or attached to an open task. Legal hold is explicit owner action only. Promotion/review decisions and audit records are durable and outlive raw events, but promotion is Phase 2, not permission to implement it here (amendment Answers to Fo; CW §§4.5,7.3,9). Open-task and legal-hold exceptions are not new retention enum members. Their expiry mechanics remain for review.

4. **Validation and failure (CW §§5,8).** Contractual semantic order: authenticate/bind, schema validate, enforce 256 KiB **per event**, redact, persist, then hash the redacted payload. No pre-redaction or rejected-content digest is stored (amendment §1); fail closed if redaction cannot complete, with no raw persistence. A defensive raw-body preflight cannot replace CW §5.1 ordering or redefine the owner-locked canonical-envelope count. Oversize is `422 event_too_large`, never truncated. Unknown `envelope_version` is 400 naming supported N and N-1 range, with migration tests. Unknown enum/schema is 422. Error bodies and conflict records have no payload. Rate limiting is 429. Count the bytes of the complete canonical serialized envelope, not the raw HTTP body or payload alone. Serialize canonical JSON using JCS and hash the redacted payload with SHA-256; redaction_version is not part of the hash identity. Redaction failure is 422 redaction_failed, with no raw persistence or payload leak. A valid canonical envelope of 262,144 bytes is at the ceiling; 262,145 bytes is 422 event_too_large. No Retry-After header on 429 or 503. A raw-body preflight may protect resources but must not redefine this contract or replace the §5.1 semantic order.

5. **Retry, conflict, ordering (CW §6; amendment §1).** Use the authenticated `(tenant, client, session, sequence)` slot and canonical post-redaction payload hash, not `event_id` alone. Same slot and hash: no-op 200, no second event. Same slot and different content: 409 and sanitized conflict record; amendment §1 limits its fields to key, both hashes, receipt time, never either payload. A lower unused sequence is accepted out-of-order, not misread as duplicate; a gap is accepted and recorded as a coverage observation. Client/adapter sequence counter persists across restart with its session ref; this is a client-conformance duty, not a guarantee the server can maintain a client's counter. Dedupe must account for retained tombstones after raw expiry without resurrecting an expired event or leaking content; retained tombstones keep the authenticated slot key, canonical redacted hash and expiry only; no raw payload or extra content.

6. **Staging and gate (CW §§7-8).** Raw events go to a dedicated recall-blind, tenant-isolated staging store, **not** existing `memory_quarantine` for proposed memories. Enforce raw-event 30-day TTL, audit tombstone on expiry and cleanup tests, subject to the frozen open-task/promotion rule and explicit legal hold; no silent extension. Until **both** 1b server-side redaction and 1c recall-blind staging/TTL exist and pass, route returns non-accepting `503 capture_disabled` with **zero writes anywhere**, including session mint/alias, audit and staging state. Never 202 before joint gate. Once enabled, a new accepted event may return 202; retry 200; bad version 400; unauthenticated 401; binding 403; conflict 409; schema/enum/size or redaction failure 422; rate limit 429; disabled 503. No dynamic runtime circuit breaker is added; retain the frozen 503 phase gate and 429 rate limit. Staged data are excluded from admin and analytics reads as well as recall.

## Owner-ruled choices and remaining implementation detail

1. 256 KiB counts complete JCS canonical serialized envelope bytes, not raw transport bytes alone.
2. JCS + SHA-256, no `redaction_version` in hash identity.
3. `422 redaction_failed` on failed redaction, without raw persistence.

5. Service-minted ULID at session open, echoed by client; optional ref is an alias; no nonce.
6. Tombstone retains authenticated slot key, canonical redacted hash, expiry only.
7. Task attachment reversible many-to-many; no bind-once rule.
8. Staged data blanket-excluded from admin/analytics reads as well as recall.
9. No dynamic runtime circuit breaker; the frozen 503 gate and 429 suffice.

These decisions settle the nine choices, not details the owner never specified: exact N/N-1 version strings and transition, concrete request/response shape for session open/echo, JCS/redaction implementation and tests, and expiry/cleanup scheduling must remain consistent with the governing contract and receive normal design review.
